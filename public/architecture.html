STEP 0 / PREPARE YOUR WORKSPACE

Before the workflow: prepare an agent and environment

A session needs both an agent ID and an environment ID. After installing dependencies and configuring the API key in step 1, reuse suitable existing resource IDs and skip steps 2–3. Create only the resources you are missing; each creation command makes a new remote resource.

Setup → conversation: configure the API key → create or reuse an agent → create or reuse an environment → save both IDs → start the app → create a session.

  1. Install dependencies and configure the API key

    Open PowerShell in lesson-c01/lesson-c01-app, the folder containing package.json. Install dependencies and create .env only if it does not already exist:

    npm install
if (!(Test-Path .env)) { Copy-Item .env.example .env }

    Enter your real ANTHROPIC_API_KEY in .env. The workspace must have Managed Agents access. The setup scripts load this file and check for a missing key before creating resources.

  2. Create the agent configuration

    npm run create-agent

    This runs scripts/create-agent.js. The agent configuration defines the model, instructions, and available tools; it is not a conversation. The script prints CLAUDE_MANAGED_AGENT_ID=.... Save that returned ID.

    The model shown below is the script's configured choice. If your workspace rejects it, select a model supported by that workspace before retrying.

  3. Create the environment configuration

    npm run create-environment

    This runs scripts/create-environment.js. It creates a reusable cloud environment configuration with limited networking and package-manager access enabled. The script prints CLAUDE_MANAGED_ENVIRONMENT_ID=.... Save that returned ID.

    This setup request creates a configuration; it does not create the conversation or demonstrate a command running in a session workspace.

  4. Save both IDs, then start the application

    Copy the printed IDs into the matching entries in .env, keeping your API key. Replace the example values below with your own:

    ANTHROPIC_API_KEY=your_api_key
CLAUDE_MANAGED_AGENT_ID=your_agent_id
CLAUDE_MANAGED_ENVIRONMENT_ID=your_environment_id
PORT=3000
    npm start

    If the server was already running, stop it with Ctrl+C and start it again to reload .env. Open http://127.0.0.1:3000 and click New session. The runtime workflow below now uses the saved agent and environment IDs.

    For the optional pending-action exercise: npm run create-pending-demo-agent creates a separate agent with a custom tool and confirmation policy. Save your original agent ID before replacing it in .env; reuse the environment ID and restart the server. This extra agent is not required for an ordinary conversation.

CONNECT THE DIAGRAM TO THE CODE

Walk through the application step by step

  1. Create the remote session · arrows 1–6

    The student clicks New session. public/app.js posts to /api/sessions. The Node.js host calls client.beta.sessions.create with the configured agent ID, environment ID, and a 50¢ list-cost budget. The SDK returns the created session and its ID to the host.

  2. Prepare observation · arrows 7–11

    The host calls attach(id). It opens events.stream(id) before reading events.list(id). The SDK buffers live delivery while history is loaded. The host keeps events in memory and deduplicates records with IDs before forwarding them. This event buffer is not a durable database.

  3. Connect the browser feed · arrows 12–14

    After preparing the host reader, the create route returns the session to the browser. The browser opens an EventSource connection to /api/sessions/:id/stream. This browser SSE connection is separate from the provider stream opened in step 2. The host sends its buffered records and forwards new events.

  4. Send a prompt · arrows 15–18

    The student enters a prompt and clicks Send message. The browser posts to /api/sessions/:id/message. The host validates the text, ensures a reader exists with attach(id), and sends a user.message through events.send. The API key remains on the host.

  5. Observe the response · arrows 19–21

    The remote session emits agent and lifecycle events. The SDK delivers them to the host, which forwards them as browser SSE. The page renders the activity feed and updates the session state. An idle event's stop reason may be end_turn, requires_action, or budget_reached; these represent different outcomes.

  6. Keep the session ID and reconnect

    A completed turn does not create a new conversation or automatically archive the session. On returning from this page in the same tab, the lab restores the last session ID. Click Connect to reopen browser SSE. The host reuses its reader if one remains; otherwise, it opens the provider stream and loads history again.

OPTIONAL BRANCHES

When the normal turn needs a host decision

Pending tool action

With a suitably configured agent, inspect the event ID and input. The browser posts the chosen response to /api/sessions/:id/action. The host sends user.tool_confirmation for Allow/Deny, or user.custom_tool_result for a supplied result. These are separate event types. Follow subsequent events to see what happens next.

Interrupt and inspect

Interrupt work posts to /api/sessions/:id/interrupt, which sends user.interrupt. Its acknowledgement is not proof the remote work stopped. Inspect session uses sessions.retrieve through the local session endpoint. Confirm idle or terminated state; navigating between pages only disconnects the browser view.

Explain it back: why are there two event streams, why must the provider stream open before history is read, and which component decides how to respond to a pending action?
